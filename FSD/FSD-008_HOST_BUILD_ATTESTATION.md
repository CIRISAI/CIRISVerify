# FSD-008 — Host build attestation: Level 1 for an embedded host

**Status:** Draft — not ratified. Specifies how a binary that statically folds CIRISVerify in (an
**embedded host**) reaches Level 1 self-verification on its own build manifest, trusted through a
grant counted by the accord holders and through no key baked into verify for the purpose, and moves
verify's own artifacts to the same path in the same release. Tracks CIRIS Constitution 1.0-rc22-pre3
and CC's answers of 2026-11-22 (§14). The build descriptor, the one manifest blob (its `format`
member, `functions_root` and the Merkle rule included) and the grant's `projects` set are **accepted
by CC, 2026-11-22; their text rides CC's next pre tag**. CC 3.1.2.1's two-plane standing text is
being rewritten to the one act of §4.2. Nothing here is implemented; §12 gives the phases.

**Cites:** CC 3.1.2.1 (the build-manifest Contribution), CC 3.1.3 (`key:record`),
CC 3.2 T2 / T3 (conferral, the un-trust lever), CC 4.2.1 (blessing a build pipeline), CC 4.5.5
(sub-scoping), CC 2.4.1 / 2.4.1.1 (composers, who may withdraw), CC 2.6.1.2 (sets), CC 2.7.5 (named
answers), CC 2.7.7 rule 2 (both count or neither), CC 5.3.2.11 (size, then digest), CC 5.3.4
(nothing a serving install signs on its own account is a root), CC 4.4.3.32 (the ladder is consumer
composition).

**Builds on:** FSD-001 (protocol, Level 1), FSD-006 (the manifest lifecycle; its §5 standing model
and its Verify surfaces are the earlier form, removed in 23.3.3 and 23.4.0), FSD-007 (trusted time,
for the one window here that reads `now`), and the edition-2 readers in
`src/ciris-verify-core/src/edition2/`.

**Rulings:** (2026-11-21) the only root is a genesis bundle's lineage. (2026-11-22) the host names
itself, and its manifests are trusted through accord-rooted standing; no second baked key.
(2026-11-22, Q8) verify's own self-check moves to this path in the same step, and one holder
ceremony grants both pipelines. (2026-11-22, Q17) an unknown withdrawal state does not fail
Level 1; it is reported beside the pass.

---

## 1. Purpose and the problem

`ciris_server` ships one wheel whose `_native*.so` statically contains verify (CIRISServer#232).
Since 22.2.3 / 23.4.2 verify finds the file its code runs from by address
(`registry::self_module_path`), recognises that the file is not one of its own artifacts
(`registry::is_embedded_in_host`), and reports it: `SelfVerificationResult.module_path`,
`.embedded_in_host`, and `error = EMBEDDED_NO_MANIFEST` (`"embedded_in_host: no manifest for host
binary"`, `src/ciris-verify-core/src/unified.rs`). That is not a pass. `unified.rs` computes
`l1_pass = binary_valid && functions_valid`, every later level chains on the one below, and the
attestation level of an embedded install is 0.

It cannot pass today for three reasons.

**Lookup.** Verify fetches `GET {registry}/v1/verify/binary-manifest/{version}?project={p}` and
`GET {registry}/v1/verify/function-manifest/{version}/{target}?project={p}`
(`RegistryClient::get_binary_manifest`, `::get_function_manifest`), with `p` the engine's configured
project (`VerifyConfig.project`, default `"ciris-verify"`) and `version` verify's own
`CARGO_PKG_VERSION`. Both name verify's artifact. Nothing names the host, and `ciris_verify_init()`
takes no configuration through which a host could name itself.

**Trust.** There is none to extend to a host.

- The binary manifest (`registry::BinaryManifest`, target → SHA-256) is unsigned JSON over web-PKI
  TLS. `docs/THREAT_MODEL.md` AV-5 states the limitation: whoever controls a registry host, or holds
  a web-PKI certificate for one, can name a replaced binary and Level 1 passes.
- The function manifest (`security::function_integrity::FunctionManifest`) carries a bound-hybrid
  signature under verify's own build key (`data/bootstrap_stewards.json`), but the path that sets
  `functions_valid` never checks it (§15 (a)). Level 1 today rests on two unsigned TLS reads.

**Format.** Both manifests are generated by `ciris-manifest-tool generate --binary --target
--version` (default `--filter ciris_verify_`; `.github/workflows/release.yml` step "Generate function
manifests") from verify's own `libciris_verify_ffi.*`. The tool reads `.symtab`, then `.dynsym`, at
generation time; the runtime check needs `{offset, size, hash}` per function and, on Android, the
`.text` file offset (`ManifestMetadata.text_section_offset`, read by `verify_functions`). A host's
manifest can be generated the same way from the host's final file. Measured by the server on
2026-11-22, the final `_native*` files of the shipped `ciris-server` 0.5.253 wheels:

| Wheel platform | Format | Size | `ciris_verify_*` functions |
|---|---|---|---|
| manylinux_2_39_x86_64 | ELF64 | 145.5 MB | 96 in `.dynsym`; no `.symtab` |
| android arm64-v8a | ELF64 | 115.1 MB | 95 in `.dynsym` |
| android armeabi-v7a | ELF32 | 85.1 MB | 95 in `.dynsym` |
| android x86_64 | ELF64 | 139.6 MB | 95 in `.dynsym` |
| win_amd64 | PE32+ DLL | 187.8 MB | 96 in the PE export table |
| macosx x86_64 / arm64 | Mach-O | 132.5 / 115.3 MB | 96 names present; not yet confirmed as exports |

Android carries 95 because one function is not built there. No function is internalized on any ELF
or PE target, so generating the manifest from the final shipped file holds there. For Mach-O it
holds once the 96 names are confirmed as exports (being checked with `ciris-manifest-tool`).

**Where it can land.** No server route serves a build manifest today (the server serves no
build-manifest or `/v1/verify/*` route), and nobody holds a pipeline grant. The 22.2.x LTS line is
edition 1 (persist 61.x) and cannot serve edition-2 Contributions. Host Level 1 is therefore a
persist v62 / server 0.6 feature. **An LTS embedded install stays at `embedded_in_host`, not a
pass.**

The pre-23.4.0 path (`manifest_contribution`, `build_attestation_bundle`,
`verify_build_manifest_via_coscrub`) is removed and is not the basis of this design; §4.4 cites it
only for what it checked.

## 2. Principles

**P1. One root, no second baked key.** The only root is a genesis bundle's lineage, anchored by the
accord holders' thumbprints verify bakes (CC 5.3.4). A host's manifest is trusted because a pipeline
holding a grant counted by that lineage's holders signed it, and for no other reason. The same
release retires verify's bootstrap build key and its registry JSON self-manifests (§12).

**P2. The reader evaluates standing.** Standing is "not a member the producer writes about itself"
(CC 3.1.2.1), and nothing a serving install signs on its own account is a root (CC 5.3.4). Verify
counts the grant itself, over signed statements, against the holders of the bundle in force. A
`standing` member in any response is never read. This replaces FSD-006 §5 / §6, where the reader
took standing from the serving node's walk.

**P3. A host cannot attest itself into a pass.** What the host says about itself (project,
version) is a lookup key (§5). The pass is decided by the bytes of the file verify runs from, the
pipeline's signed row, and the reader's own count of the grant.

**P4. Measurements, not tiers.** Verify reports what it measured, in flat fields named for the
measurement (§8). It defines no "host tier" and no standing grade. The ladder is consumer
composition (CC 4.4.3.32); `l1_pass` stays the one derived boolean verify already computes.

**P5. Absence is a signal; over-claim is the lie.** A missing manifest, an unreachable route or a
row not yet held is reported as what it is. A row that names a different binary from the one
running is a refutation and is reported as one.

**P6. Fail-secure, and never a silent pass.** Every link of the claim chain must conclude Valid for
a pass: a Waiting row, an undecidable window, a grant short of its count, a blob not held each leave
`l1_pass` false and say why. The one thing a reader cannot conclude from what it holds is that no
withdrawal exists; that view is always reported beside the pass (§7.3), so no pass is silent about
it.

### 4.1 Stages 1–2: the pipeline key and its record

The pipeline holds one composite key (CC 2.6.1.7). Its `key:record:v1` is the key's claim of itself,
admitted by proof of possession (CC 3.1.3). It **states `valid_until`**, at most
`key_record_max_secs` (365 days) after its `asserted_at`, and renews by a `supersedes` of its own
record; a renewal is not an end (CC 2.4.1.1, Q11). A build row lapses only when the key has ended
and no row that has not lapsed names it: a live node's `attestation:self_verify` naming the build row
keeps it from lapsing (CC 2.4.1.1). After a pipeline key truly ends, an old build with no live
attester has no un-lapsed manifest (§11 HB-14). Rotation is the one rotation shape of CC 3.1.3.
Verify reads the record through `KeyRecordDirectory` as it reads every other.

### 4.2 Stage 3: the grant (one kind of act)

A pipeline's standing is `infra:attest` conferred by **one** kind of act (ruling 2026-11-21; CC
3.1.2.1's text is being rewritten to it):

- a **row** of family `trust:confers` (a `delegates_to` bearing `trust:confers:v1`, optionally
  narrowed); CC is making `trust:blessing` and `trust:confers` one family, and this design does not
  depend on the `trust:blessing` name;
- **counted** over a strict majority of the holders of the bundle in force, one voice per holder,
  each under the key that bundle seats for it;
- naming that bundle in `refs.head`, and naming the pipeline's key record by row id;
- carrying the scope `infra:attest`, or the sub-scope `infra:attest:provenance:build_manifest` (CC
  4.5.5: narrower only, and a child never satisfies a check for its parent);
- carrying `projects`, a set under CC 2.6.1.2 (sorted, no duplicates, non-empty when present) beside
  `scope` in the grant's payload; a narrowed onward grant lists a subset; a grant with no `projects`
  grants no project (accepted by CC, 2026-11-22);
- **plus the owner's acceptance** (CC 3.2 T3, CC 3.1.1; ruled by CC 2026-11-22): a pipeline key is
  a machine identity bound to its owner (a person) by an owner-binding, and the acceptance is that
  owner's `trust:accepts:v1` edge to the root whose holders granted, "a person's row that every node
  and agent they own reads". It is **one edge per root, not one per grant**, and the pipeline's own
  key never accepts. A pipeline with no owner has no acceptance, and its grant confers nothing.

**Scope matching (CC 4.5.5, normative).** The check asks "may this key attest family F". A held
`infra:attest` satisfies it; a held `infra:attest:F` satisfies it; nothing else does. A child never
satisfies a check for its parent, an unrecognised sub-scope is never widened to its parent, and the
match is on whole tokens across a `:` boundary, never a prefix test (`infra:attest_assurance` is a
different capability). A build pipeline's grant carries `infra:attest:provenance:build_manifest`, and
the ceremony issues that narrowest form with `projects`. A bare `infra:attest` on a pipeline is
valid and confers every attest family, but `projects` is required of a build manifest whatever the
scope string: a grant with no `projects` confers a build manifest for no project.

There is no other plane, no key-root delegation and no baked key. The genesis bundle's charter
`scope` holding `infra:attest` (`edition2::genesis::REQUIRED_SCOPE`) is the root's scope and confers
nothing on a pipeline. The minted genesis seats three holders and one serve seat; nobody holds a
pipeline grant today. A grant is a row counted over 2 of the 3 holders with the pipeline's owner
accepting; **one holder ceremony grants both pipelines**, the server's and verify's, and scheduling
it is Eric's (§13).

**How a grant ends (CC 2.4.1.1, Q10).** A grant is two consents, and either ends it: (a) a counted
`withdraws` of the grant row by a strict majority of the holders of the bundle in force, naming the
head it acts from; or (b) the owner's withdrawal of the `trust:accepts` edge, which gives up
everything that root confers on everything the owner owns. An owner who gives up one grant and keeps
the root ends the pipeline's key or its owner-binding instead. Revoking the pipeline's **key** is a separate act that ends what the
key signs afterwards (`revoked_after`). A reader's own un-trust of the root ends the grant for that
reader; for verify the root is its baked anchor.

### 4.3 Stage 4: the manifest blob

§6. It is generated from the **final** file that ships, after every post-link rewrite (auditwheel's
patchelf, delocate, code signing, Android packaging), because the binary hash and the function
offsets are properties of that file.

### 4.4 Stage 5: the build row

One row per (signer, project, version, target), on `provenance:build_manifest:{target}:v1`, signed
by the pipeline (authored; `subject_key_ids` empty; `cohort_scope: federation`;
`evidence_refs: [manifest_hash]`). Accepted by CC, 2026-11-22:

| `build` member | Rule |
|---|---|
| `project` | tstr, `[a-z0-9-]`, 1..=64 bytes; required |
| `version` | tstr, 1..=64 bytes, compared byte for byte; required |
| `manifest_hash` | bare lowercase hex SHA-256 of the blob; required |
| `manifest_size` | the blob's byte length, `u64 > 0`; required |

The target is the dimension's `{target}`; `sub` carries none of these. A later row by the same
signer at the same (project, version, target) is a `supersedes` naming the earlier row in
`refs.target`. Two standing rows at the same three outside one `supersedes` chain are both refused,
`build_manifest_equivocation` (CC 2.7.7 rule 2: both count or neither). A rebuild is normally a new
version, hence a new row; a bad build is withdrawn by its pipeline (CC 3.1.2.1).

The removed `verify_build_manifest_contribution` checked kind, signer, signature, scope, dimension,
`evidence_refs` and binary-hash form. On edition 2 the row reader and family check cover signer and
signature, §7 keeps the rest, the binary hash moves into the blob, and no `delegation_scope` is
carried: standing is counted, never written.

Publication and fetch (stages 6–7) are §9; the reader's checks (8–12) are §7.

### 4.5 Stage 13: comparison against the running module

- **Binary.** `registry::compute_self_hash` hashes the file `self_module_path` names with
  `binary_format::canonical_binary_hash` (whole file on ELF and PE; the page-aligned `__TEXT` region
  on Mach-O) and compares it in constant time with the blob's `binary_hash`.
- **Functions.** `function_integrity::verify_functions` resolves the code base of the module holding
  `self_code_address`, which for a host is the host's image, so the blob's offsets are read against
  the right image. Every entry must match; the opaque-failure rule of FSD-001 holds.
- **iOS.** Function hashes do not survive App Store re-signing. The FFI's existing compensation
  (App Attest standing in for function integrity at L1) is unchanged by this FSD.

### 4.6 Stage 15: presenting

A running node's statement that it runs the build is `attestation:self_verify`, signed by the
running node about itself (settled by CC, Q1; not `agent_integrity`). It cites the **host**
pipeline's Contribution: `evidence_refs` carries the manifest blob's digest, and the named row
(`references_attestation_id`) is the Contribution's row id. Verify supplies the verified inputs
(`manifest_row_id`, `manifest_hash`, §8); the node signs the row. A verify producer for it is not in
this FSD's phases.

## 5. How the host names itself

**Configuration.** `VerifyConfig` gains `host: Option<HostIdentity>`, `HostIdentity { project:
String, version: String }`, under the descriptor's rules (§4.4). `VerifyConfig.project` keeps naming
verify's own registry namespace and is unchanged.

**FFI.** New `ciris_verify_init_with_config(config_json)` taking `{ "host_project": "...",
"host_version": "..." }` (both or neither; one alone is refused); `ciris_verify_init()` stays as the
zero-config form. Python: `CIRISVerify(host_project=..., host_version=...)`. The host's wheel passes
its own distribution name and `__version__`.

**Why it is only a lookup key.** The pair selects which offline set to fetch. It decides nothing:

1. the blob must name the running file's measured `binary_hash`, so a false name finds a row about
   other bytes (`binary_valid` false, a refutation) or no row (absence);
2. the reported project and version are the **row's** (`manifest_project`, `manifest_version`); the
   configured pair is echoed separately (`host_project_claimed`, `host_version_claimed`) and
   `manifest_names_host` records whether they agree;
3. a host that names an older version of itself can only match a row for the bytes actually
   running, which is that older build (§11 HB-5).

A host that configures nothing while embedded keeps today's result: `embedded_in_host: true`,
`error: EMBEDDED_NO_MANIFEST`, not a pass. Verify's own artifact needs no configuration: it looks
itself up as project `ciris-verify` at its `CARGO_PKG_VERSION`, by the same route and the same checks.
A non-embedded install that configures a host pair has it ignored and reported
(`host_ignored_not_embedded: true`).

## 6. The manifest blob (one format)

One blob per (project, version, target) carries the binary hash and the function table, so one
signature covers both. Accepted by CC, 2026-11-22:

```
build-manifest-blob = {
  "format":         "ciris-binary-manifest/1",   ; first member
  "project":        tstr,    ; = build.project
  "version":        tstr,    ; = build.version
  "target":         tstr,    ; = the row's dimension {target} = current_target()
  "binary_hash":    tstr,    ; bare lowercase hex, canonical_binary_hash of the final file
  "functions_root": bstr .size 32,              ; always
  ? "functions":    { + tstr => { "offset": uint, "size": uint, "hash": tstr } },
  "generated_at":   tstr,    ; the generator's instant; informative, the row's asserted_at is the signed one
  "tool":           tstr     ; the generator and its version, e.g. "ciris-manifest-tool/23.6.0"
}
```

A blob whose `project`, `version` or `target` differs from the row's is refused,
`build_manifest_descriptor_mismatch`.

**The function table (CC, Q15): one form, no threshold.** The blob always carries `functions_root`.
Each leaf is `CDE({name, offset, size, hash})`, leaves in the byte order of the function names; a
leaf is hashed under the RFC 6962 prefix `0x00`, a node is SHA-256 over `0x01`, left and right; a
non-power-of-two count is padded by repeating the last leaf to the next power of two, the locale
tree's rule (CC 3.1.2). An inline `functions` table is optional; when present the reader recomputes
the root from it and refuses a difference (`build_manifest_functions_root_mismatch`, verify's
token). A table carried as its own blob is committed by the root, and the row may cite that blob in
`evidence_refs`; the reader fetches it and checks it against the root the same way. A table of zero
functions is refused.

**Kept from today.** From `BinaryManifest`: the one target's hash (`binaries[target]`), and
`version`. From `FunctionManifest`: `target`, `binary_hash`, `binary_version` (as `version`),
`generated_at`, and `functions` with each `FunctionEntry`'s `offset`, `size` and `hash`.
**Dropped:** `BinaryManifest`'s map of every target (one blob is one target); `FunctionManifest`'s
format `version` (superseded by `tool`), `manifest_hash` (the blob's address is its digest; the old
member hashed function hashes only), `signature` and its `key_id` (the row is the signature), each
entry's `name` duplicate (the map key) and `first_bytes` (a debugging aid), and `ManifestMetadata`.
**Added:** `format`, `project`, `functions_root`, `tool`.

**Offsets (decided by verify, Q16).** `verify_functions` on Android reads
`ManifestMetadata.text_section_offset` today. The blob carries no metadata member: the manifest tool
emits offsets already relative to the base the runtime resolves, and the tool and `verify_functions`
change together. The binary-hash rule (whole file, or Mach-O `__TEXT`) is
`binary_format::canonical_binary_hash`'s, recorded by `tool`.

**Encoding (CC, Q13).** CC 2.6.1.2's deterministic encoding, no floats, and **no `typ`**: the blob is
not a signed object. So two producers given the same final file emit the same bytes, and anyone can
recompute `manifest_hash` from the binary. It is registered in CC 3.1.2.1 with a CDDL in CC's
`manifests/`; verify writes the CDDL and the known answers. `ciris-manifest-tool generate` gains
`--project` and the blob output; with no `.symtab` it uses `.dynsym`.

## 7. The reader's checks, in order

Inputs (all bytes, all re-verified offline from the anchor): the genesis bundle's statements and
the rows it names; the build row's statements; the blob; the pipeline's `key:record` statements;
the grant's statements, every voice; the grantee's acceptance; any composers held for the build row
and the grant (`supersedes`, `withdraws`, `recants`); the revocation snapshot when there is one
(#338); and `now` as trusted time (FSD-007), for the grant's window only.

1. **Root.** `edition2::genesis::read_genesis_bundles` from verify's baked anchor
   (`Anchor::Thumbprints`) gives the bundle in force and its holders' composite keys. No bundle
   Valid: every later step is `waiting:root` (this is the trust root Level 3 measures; the ladder
   order is unchanged, and the dependency is stated in `grant_root`).
2. **Row.** `edition2::verify_row_statement` under a `KeyRecordDirectory` holding the pipeline's
   record: Valid, Invalid (token) or Waiting. Then `family::verify_row_in_family` under
   `VendoredFamilyModel` (authored, no second signers), the family matched through
   `namespace_match`. The blob is not touched until the descriptor it is checked against is signed.
3. **Descriptor.** All four `build` members present and well formed (§4.4); `evidence_refs` names
   `manifest_hash`; `subject_key_ids` empty; `cohort_scope: federation`.
4. **Size, then digest** (CC 5.3.2.11). The blob's length equals `manifest_size`, or refuse without
   hashing (`manifest_size_mismatch`); then SHA-256 equals `manifest_hash` in constant time
   (`manifest_hash_mismatch`); then the closed decode, `format` first; then `functions_root`
   against the inline table, or against the table blob once fetched (§6).
5. **Agreement.** The blob's `project`, `version`, `target` equal the descriptor's and the
   dimension's; `target` equals `registry::current_target()`. Otherwise
   `build_manifest_descriptor_mismatch`.
6. **Grant.** §7.1.
7. **Row state.** §7.2.
8. **Compare** (§4.5). Only now is the blob's function table used.

`binary_valid` is true iff steps 1–7 conclude Valid / counted / live and the binary hash matches.
`functions_valid` is true iff `binary_valid` and every function in the blob matches. A Waiting at
any step is reported with what is missing (CC 2.7.5 **missing**), not as a failure.

### 7.1 The grant (new: verify has no edition-2 evaluator for it)

Verify has no reader for a counted `trust:confers` row today; this is the main
new work. `evaluate_pipeline_grant(&GrantInput) -> GrantReading::{Valid { row_id }, Absent,
Waiting(missing), Refused(token)}`. The statements of each candidate row are read together
(`family::verify_group_row_in_family`, act `group`), and the row gives standing iff:

1. its `refs.head` names the bundle in force (a row naming another bundle waits for it, as
   `edition2::accord_halt::HaltRoster::find_by_head` does for halt rows);
2. one voice per holder `iss`, each under the key that bundle seats for it, reaches a strict
   majority of that bundle's holders; short, with unheld keys that could make it up, is Waiting; the
   count is the one `edition2::accord_halt::verify_lifecycle_row` already makes;
3. its payload names the pipeline's key record by row id, and that record's key is the build row's
   `kid`;
4. its scope is `infra:attest` or `infra:attest:provenance:build_manifest` and nothing else; any
   other scope, alone or beside these, refuses the row (`pipeline_grant_out_of_role`; CC, Q18); a
   sub-scope of another family never satisfies this check (CC 4.5.5);
5. `projects` is a well-formed set and holds `build.project`; otherwise
   `build_manifest_project_not_granted` (an absent or empty set grants no project);
6. the pipeline's owner-binding and its owner's `trust:accepts:v1` edge to the granting root are
   held and standing (a statement by the pipeline's own key is not an acceptance); otherwise
   Waiting;
7. a stated term (`delegation_valid_from` / `delegation_valid_until` on a `confers` row) covers
   `now`; an undecidable comparison under FSD-007 §4.5 is not covered;
8. the grant has not ended (§4.2): no counted `withdraws` of it by a strict majority of the holders
   of the bundle in force, and no withdrawal of the grantee's acceptance; and it is either not
   superseded or superseded with the build row's `asserted_at` before the successor's (CC 3.2 T2:
   rotation keeps lineage).

The pipeline key must be live at the build row's `asserted_at`: a record covers it and no own
`key:revocation` whose `revoked_after` precedes it, from the snapshot where there is one.

### 7.2 Row state

`build_row_state(row, composers, peers) -> RowState::{Live, Superseded { by }, Withdrawn, Recanted,
Equivocated}`:

- **withdrawn** (the pipeline's `withdraws`, CC 2.4.1.1 rule 1; nothing reaches the row through
  `subject_key_ids`, which is empty): retired, so a node running that build **fails** Level 1;
- **superseded** at the same (project, version, target): replaced, so a binary matching only the
  superseded manifest **fails**;
- **recanted**: fails, reported as itself;
- **equivocated**: two standing rows by one signer at the same three outside one `supersedes` chain
  are both refused, `build_manifest_equivocation` (CC 2.7.7 rule 2).

### 7.3 The withdrawal view

The revocation snapshot carries revoked **keys** and entities, never row withdrawals. A withdrawal
reaches the reader as the `withdraws` row itself, so Level 1 reads the row plane as well as the
snapshot. A reader can verify a withdrawal it holds; it cannot prove from what it holds that none
exists. Verify therefore reports the view it had, always:

| `withdrawal_state` | Meaning |
|---|---|
| `withdrawn` / `superseded` / `recanted` | a composer was held and verified; not a pass |
| `none_held` | the row plane was read (`withdrawal_source`, `withdrawal_as_of_ms`) and no composer was held |
| `unknown` | the row plane could not be read: offline, or the route returned no composer view |

**Ruled (Eric, 2026-11-22, Q17):** `unknown` and `none_held` do not fail Level 1. A verified
manifest passes, and the view is always reported beside the pass with its as-of instant, so no pass
is silent about it. Consumer policy decides: one that needs a fresh view requires
`withdrawal_state: none_held` with a recent `withdrawal_as_of_ms`.

## 9. The read route

No route exists today. CC 5.3.5 still names `GET /v1/verify/build-manifest/{project}/{version}/{target}`
("returns the verbatim signed BuildManifest"); the two must be reconciled (Q19). The server's
proposed route (its design item; Server and Edge own the door):

```
GET /v1/provenance/build/{project}/{version}/{target}
```

It returns one read-only offline set that any node holding the rows can serve, from which an
install verifies everything from its anchor with no further fetch (CC's list, Q6):

| Member | Content |
|---|---|
| `bundle` | the genesis bundle's statements and the rows it names (also fetchable from the seats' dial hints) |
| `row` | each statement of the build row |
| `blob` | the manifest blob (size before hash) |
| `key_record` | each statement of the pipeline's `key:record` |
| `grant` | each statement of the counted grant, every voice |
| `acceptance` | the grantee's acceptance statements |
| `composers` | **asked of the server:** every `supersedes` / `withdraws` / `recants` the serving node holds naming the build row or the grant, and every other standing row by the same signer at the same (project, version, target) |
| `composers_as_of` | **asked of the server:** the serving node's instant for that view (unsigned) |

Everything is bytes the reader re-verifies; any summary, `standing` or `served_by` member is
ignored. The withdrawal check needs the row plane (§7.3). Verify asks that the same route carry
`composers` as above, so one fetch answers it; failing that, a second call by row id
(`GET /v1/provenance/composers/{row_id}`, the server's to name) does. Without either,
`withdrawal_state` is `unknown`. A serving node that withholds a composer hides a withdrawal from that
reader (HB-6); it cannot forge a pass. A blob too large to serve inline is fetched by digest from a
holder named by `custody:ack:v1`, checked as §7 step 4 says.

### 10.1 Offline: the manifest cache

`manifest_cache::SignedManifestCache` today stores the `BinaryManifest`, the `FunctionManifest` and
an agent build record, signed by the device's hardware Ed25519 key, with no expiry; its stated
provenance is "the signature proves successful registry verification". Under this FSD the cache
stores the offline set of §9, not a verdict: every statement and the blob, with the bundle id they
were counted under and `withdrawal_as_of_ms`.

On load every item is re-verified by the pure tier exactly as if fetched (§7). The device signature
keeps its use as a tamper signal on the cache file and confers nothing: a cache whose rows do not
verify is not a pass whatever signs it. A cached pass reports `manifest_source: cache`,
`withdrawal_source: cache` and the cached `withdrawal_as_of_ms`. A grant term is re-read against
`now` on every load. No cached item expires by age (CC 3.2 T4).

## 11. Threats

In the style of `docs/THREAT_MODEL.md` §3. Proposed for that document as AV-63 onward (FSD-007
proposes AV-53 to AV-62).

#### HB-1: A host lies about its project or version

**Attack:** configure another project's name, or a newer version, to borrow its manifest.
**Mitigation:** a lookup key only (§5); the blob must name the measured hash, and reported project
and version are the row's. **Residual:** none; `manifest_names_host: false` is the trace.

#### HB-2: Stolen pipeline key

**Attack:** sign a build row for a modified host.
**Mitigation:** the modified build passes only while the key and its grant hold, and only for the
projects the grant lists. The pipeline revokes its key (`key:revocation:v1` with `revoked_after`,
carried by the snapshot); the holders withdraw the grant by a cosigned `withdraws` (CC 3.2 T2: no
lineage, standing ends at once). Custody of the pipeline key in hardware raises the cost.
**Residual:** rows signed before the effective `revoked_after` stand (a key revocation ends what the
key signs afterwards, not the grant); a node that has not received the revocation or withdrawal
passes until it does (HB-6). The grant ends by the holders' counted `withdraws` or the grantee's own
withdrawal of its acceptance (§4.2).

#### HB-3: A grant wider than `infra:attest`

**Attack:** a grant carrying more, so a pipeline compromise reaches further.
**Mitigation:** any other scope refuses the grant (`pipeline_grant_out_of_role`); the sub-scope
narrows the family, and a child never satisfies its parent (CC 4.5.5). **Residual:** a grant of the
parent `infra:attest` reaches every `infra:attest` family; the server SHOULD grant the sub-scope.

#### HB-4: One pipeline attests another project's build

**Attack:** a pipeline granted for project A signs a row naming project B. **Mitigation:** the
grant's `projects` set (`build_manifest_project_not_granted`). **Residual:** a set listing too much is
the holders' counted act.

#### HB-5: Replay of an old manifest for a vulnerable build

**Attack:** run an old, vulnerable, never-withdrawn build of the host and claim its version.
**Mitigation:** the row is genuine and the bytes are that build, so L1 truthfully passes for that
build; `manifest_version` and `manifest_asserted_at_ms` say which. A bad build is withdrawn by its
pipeline, which ends the pass (HB-6).
**Residual:** L1 proves which build runs, not that it is safe. A minimum version is consumer policy.

#### HB-6: A withdrawn build still running

**Attack:** keep running after the pipeline withdraws the build, relying on the node not hearing.
**Mitigation:** composers ride the offline set (§9); a held `withdraws` ends the pass. Every result
states `withdrawal_state`, `withdrawal_source` and `withdrawal_as_of_ms`.
**Residual:** the snapshot does not carry row withdrawals, so an offline node, or a serving node that
withholds the composer, leaves the reader at `unknown` or a stale `none_held`. By Eric's ruling
(Q17) that still passes, reported with its as-of instant and never silent; consumer policy decides.

#### HB-7: The registry serves a different blob

**Attack:** other bytes, or another length, under the row.
**Mitigation:** size, then full SHA-256 against the signed descriptor, before decode (CC 5.3.2.11).
**Residual:** denial of the pass only.

#### HB-8: A function manifest covering only a few functions

**Attack:** the blob lists few functions, so most code is unchecked in memory.
**Mitigation:** the reader reports `functions_in_manifest`; zero functions refuses the blob. The
whole-file hash covers every byte on disk.
**Residual:** the in-memory check covers exported functions only (95–96 `ciris_verify_*` on the measured
server builds); a patch to unexported code after load is not seen. A coverage floor is consumer
policy.

#### HB-9: Target or ABI confusion

**Attack:** a row for another target (simulator on device, glibc on musl, a triple for an ABI).
**Mitigation:** dimension and blob must name `current_target()`; the binary hash binds one file.
**Residual:** none beyond HB-8.

#### HB-10: Equivocating rows

**Attack:** two rows for one (project, version, target), naming two binaries, shown to two readers.
**Mitigation:** a reader holding both refuses both, `build_manifest_equivocation` (CC 2.7.7 rule 2);
the route serves every standing row at the three. **Residual:** a reader shown one cannot tell.

#### HB-11: The host tampers with verify in its own address space

**Attack:** patch verify's code or result after load. **Mitigation:** the function check reads the
mapped image. **Residual:** inherent, as for a hostile process loading the library; remote readers
rely on L2 and the node's signed `attestation:self_verify`.

#### HB-12: The route withholds the set or part of it

**Attack:** omit the row, grant or acceptance. **Mitigation:** absence is reported as absence
(`EMBEDDED_NO_MANIFEST`, `grant_verdict: absent`, `waiting:{what}`). **Residual:** denial of L1.

#### HB-13: Rolled-back cache

**Attack:** restore an older cache to hide a withdrawal. **Mitigation:** cached items re-verify; the
view's instant is reported. **Residual:** offline, the older view stands until the next fetch.

#### HB-14 (limit): An old build outlives its pipeline key

**Case:** the pipeline key's record reaches `valid_until` without renewal, or the key revokes
itself, and an old build is still installed.
**Effect:** the old build's row lapses unless a live row names it (CC 2.4.1.1). A node whose own live
`attestation:self_verify` names the row keeps it; a fresh install of that build, with no live
attester, finds no un-lapsed manifest and does not pass.
**Mitigation:** the pipeline renews its record by `supersedes` (renewal is not an end) for as long as
its builds are meant to run.
**Residual:** by design, a build whose pipeline has truly ended cannot newly reach Level 1.

#### HB-15 (limit): The hard cut

**Case:** from the release of Phase 2 the registry JSON self-manifests and the bootstrap keyset are
gone (§12).
**Effect:** no install, embedded or verify's own, passes Level 1 until the grant ceremony has run
and the pipelines have published rows for that release.
**Mitigation:** ship Phase 2 only after the ceremony and the first published rows (§13).
**Residual:** until then every install reports Level 1 not passed, with `grant_verdict` and
`manifest_row_verdict` saying which link is missing. That is fail-secure, not a regression to
unsigned trust.

## 15. Findings in the current code and docs

- **(a) Level 1 does not check the function manifest's signature.** `functions_valid` is computed
  by `UnifiedAttestationEngine::run_self_verification_with_manifests` (`unified.rs`), which calls
  `function_integrity::verify_functions` on the manifest `RegistryClient::get_function_manifest`
  fetched, with no signature check. The signature is checked only in the FFI constructor,
  `constructor::early_verify` → `run_verification` → `verify_manifest_signature` against
  `get_trusted_stewards`; its result goes to the response's separate `function_integrity` string and
  never reaches `functions_valid` or `l1_pass`.
- **(b)** `release.yml` passes no `--filter`; `ciris_verify_` is `ciris-manifest-tool`'s default.
- **(c)** `holds_bytes:sha256:{prefix}` is retired in rc22; the holder directory is `custody:ack:v1`
  (CC 3.1.3.3). FSD-006 stages 7 and 10 still name it.
- **(d)** FSD-006 §5 / §6 take standing from the serving node's walk; CC 3.1.2.1 and CC 5.3.4 make the
  reader evaluate it. This FSD replaces that model for Level 1.
