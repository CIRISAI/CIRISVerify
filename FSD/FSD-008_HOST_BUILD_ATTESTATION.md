# FSD-008 — Host build attestation: Level 1 for an embedded host

**Status:** Draft — not ratified. Specifies how a binary that statically folds CIRISVerify in (an
**embedded host**) reaches Level 1 self-verification on its own build manifest, trusted through a
grant counted by the accord holders and through no key baked into verify for the purpose, and moves
verify's own artifacts to the same path in the same release. Tracks CIRIS Constitution 1.0-rc22-pre4
and CC's answers of 2026-11-22 (§14). The build descriptor, the one manifest blob and the grant's
`projects` set are accepted by CC (2026-11-22); their text rides CC's next pre tag, with CC 3.1.2.1
rewritten to the one standing act of §4.2. **Phase 1a (the blob codec) and Phase 1b (the standing
walk) are built in 23.6.0**; Phase 2 (host fetch and wiring, verify's own self-check on the row
path, retiring the baked key) is not (§12).

**Cites:** CC 3.1.2.1 (the build-manifest Contribution), CC 3.1.3 (`key:record`), CC 3.2 (the
owner-binding; T2 / T3, conferral and the un-trust lever), CC 4.2.1 (blessing a build pipeline),
CC 4.5.5 (sub-scoping), CC 2.4.1 / 2.4.1.1 (composers, who may withdraw, "An act names its head"),
CC 2.6.1.2 (sets), CC 2.6.1.9 (counted rows), CC 2.7.5 (named answers), CC 2.7.7 rules 2 and 6,
CC 3.1.3.2 (contested replies), CC 5.3.2.11 (size, then digest), CC 5.3.4 (nothing a serving
install signs on its own account is a root), CC 4.4.3.32 (the ladder is consumer composition).

**Builds on:** FSD-001 (protocol, Level 1), FSD-006 (the manifest lifecycle; its §5 standing model
and its Verify surfaces are the earlier form, removed in 23.3.3 and 23.4.0), FSD-007 (trusted
time), CIRISKernel's two-standings model (fa1dc1d, §J), and the edition-2 readers in
`src/ciris-verify-core/src/edition2/`.

**Rulings:** (2026-11-21) the only root is a genesis bundle's lineage. (2026-11-22) the host names
itself, and its manifests are trusted through accord-rooted standing; no second baked key.
(2026-11-22, Q8) verify's own self-check moves to this path in the same step, and one holder
ceremony grants both pipelines. (2026-11-22, Q17) an unknown withdrawal state does not fail
Level 1; it is reported beside the verdict.

## 1. Purpose and the problem

`ciris_server` ships one wheel whose `_native*.so` statically contains verify (CIRISServer#232).
Verify finds the file its code runs from by address (`registry::self_module_path`), recognises that
the file is not one of its own artifacts (`registry::is_embedded_in_host`), and reports it:
`SelfVerificationResult.module_path`, `.embedded_in_host`, and `error = EMBEDDED_NO_MANIFEST`
(`"embedded_in_host: no manifest for host binary"`, `src/ciris-verify-core/src/unified.rs`). That is
not a pass. `unified.rs` computes `l1_pass = binary_valid && functions_valid`, every later level
chains on the one below, and the attestation level of an embedded install is 0.

It cannot pass on the current Level 1 path for three reasons.

**Lookup.** Verify fetches `GET {registry}/v1/verify/binary-manifest/{version}?project={p}` and
`GET {registry}/v1/verify/function-manifest/{version}/{target}?project={p}`
(`RegistryClient::get_binary_manifest`, `::get_function_manifest`), with `p` the engine's configured
project (`VerifyConfig.project`, default `"ciris-verify"`) and `version` verify's own
`CARGO_PKG_VERSION`. Both name verify's artifact. Nothing names the host, and `ciris_verify_init()`
takes no configuration through which a host could name itself.

**Trust.** There is none to extend to a host.

- The binary manifest (`registry::BinaryManifest`, target → SHA-256) is unsigned JSON over web-PKI
  TLS. `docs/THREAT_MODEL.md` AV-5 states the limitation: whoever controls a registry host, or holds
  a web-PKI certificate for one, can name a replaced binary and Level 1 passes.
- The function manifest (`security::function_integrity::FunctionManifest`) carries a bound-hybrid
  signature under verify's own build key (`data/bootstrap_stewards.json`), but the path that sets
  `functions_valid` never checks it (§15 (a)). Level 1 rests on two unsigned TLS reads.

**Format.** Both manifests are generated by `ciris-manifest-tool generate` from verify's own
`libciris_verify_ffi.*`. The runtime check needs `{offset, size, hash}` per function and, on
Android, the `.text` file offset (`ManifestMetadata.text_section_offset`, read by
`verify_functions`). A host's manifest is generated from the host's final file. Measured by the
server on 2026-11-22, the final `_native*` files of the shipped `ciris-server` 0.5.253 wheels:

| Wheel platform | Format | Size | `ciris_verify_*` functions |
|---|---|---|---|
| manylinux_2_39_x86_64 | ELF64 | 145.5 MB | 96 in `.dynsym`; no `.symtab` |
| android arm64-v8a | ELF64 | 115.1 MB | 95 in `.dynsym` |
| android armeabi-v7a | ELF32 | 85.1 MB | 95 in `.dynsym` |
| android x86_64 | ELF64 | 139.6 MB | 95 in `.dynsym` |
| win_amd64 | PE32+ DLL | 187.8 MB | 96 in the PE export table |
| macosx x86_64 / arm64 | Mach-O | 132.5 / 115.3 MB | 96, each with an offset and a size (`ciris-manifest-tool list-functions` on the shipped files; the same 96 names on both) |

Android carries 95 because `ciris_verify_tpm_attestation` is gated off there by design
(`#[cfg(not(any(target_os = "android", target_os = "ios")))]` in the FFI: no TPM path on mobile).
No function is internalized on any ELF, PE or Mach-O target, so generating the manifest from the
final shipped file holds on all seven.

**Where it can land.** No server route serves a build manifest yet, and nobody holds a pipeline
grant. The 22.2.x LTS line is edition 1 (persist 61.x) and cannot serve edition-2 Contributions.
Host Level 1 is a persist v62 / server 0.6 feature. **An LTS embedded install stays at
`embedded_in_host`, not a pass.**

The pre-23.4.0 path (`manifest_contribution`, `build_attestation_bundle`,
`verify_build_manifest_via_coscrub`) is removed and is not the basis of this design.

## 2. Principles

**P1. One root, no second baked key.** The only root is a genesis bundle's lineage, anchored by the
accord holders' thumbprints verify bakes (CC 5.3.4). A host's manifest is trusted because a pipeline
holding a grant counted by that lineage's holders, and accepted by the pipeline's owner, signed it.
Phase 2 retires verify's bootstrap build key and its registry JSON self-manifests (§12).

**P2. The reader evaluates standing.** Standing is "not a member the producer writes about itself"
(CC 3.1.2.1), and nothing a serving install signs on its own account is a root (CC 5.3.4). Verify
counts the grant itself, over signed statements, against the holders of the bundle the grant names.
A `standing` member in any response is never read.

**P3. A host cannot attest itself into a pass.** What the host says about itself (project,
version) is a lookup key (§5). The pass is decided by the bytes of the file verify runs from, the
pipeline's signed row, and the reader's own walk.

**P4. Measurements, not tiers.** Verify reports what it measured, in flat fields named for the
measurement (§8). It defines no "host tier" and no standing grade. The ladder is consumer
composition (CC 4.4.3.32); `l1_pass` stays the one derived boolean verify already computes.

**P5. Absence is a signal; over-claim is the lie.** A missing manifest, an unreachable route or a
row not yet held is reported as what it is (Waiting, with what it waits on). A row that names a
different binary from the one running is a refutation and is reported as one.

**P6. Fail-secure, and never a silent pass.** Every link of the claim chain must conclude for a
pass. The one thing a reader cannot conclude from what it holds is that no withdrawal exists; that
view is always reported beside the verdict (§7.5), so no pass is silent about it.

### 4.1 The pipeline key and its record

The pipeline holds one composite key (CC 2.6.1.7). Its `key:record:v1` is the key's claim of itself,
admitted by proof of possession (CC 3.1.3). As a `node` or `agent` record it **states
`valid_until`**, at most `key_record_max_secs` (365 days) after its `asserted_at`, and renews by a
`supersedes` of its own record; a renewal is not an end (CC 2.4.1.1). A build row lapses only when
the key has ended and no row that has not lapsed names it: a live node's `attestation:self_verify`
naming the build row keeps it from lapsing. Statements reach the walk's readers through the caller's
`KeyDirectory`, which reads instants from the rows.

### 4.2 The grant (one kind of act)

A pipeline's standing is `infra:attest` conferred by **one** kind of act, a `trust:confers` row (CC
is folding `trust:blessing` into `trust:confers`; the walk does not read the `trust:blessing`
name). `grant_counted` reads it:

- a `delegates_to` row of family `trust:{job}:{version}`, dimension `trust:confers:v1`, **counted**
  (no `author`), the grantee its CWT `sub` (an identity reference), `refs.head` the bundle it is
  counted over;
- `scope` a set (CC 2.6.1.2: sorted, no repeat, non-empty) and, for a pipeline, `projects` a set
  beside it. A grant carrying `projects` may carry only `infra:attest` and
  `infra:attest:provenance:build_manifest` (`pipeline_grant_out_of_role`). Every other member of
  the payload is open;
- its voices are statements over one row id, each by a holder of the bundle `refs.head` names under
  the key that bundle seats for it, one voice per holder, counted at `2·yes > N` of that bundle's
  holders (`count::strict_majority`, the one count the halt reader `accord_halt` and the genesis
  reader `genesis` also use; in a later genesis bundle the count is over the predecessor's holders,
  so a holder's voice counts toward the bundle that removes them);
- a statement under a key the named bundle does not seat is not a voice and refuses nothing; a
  statement's own fault refuses that statement only; among statements over several row ids the row
  with the most distinct voices is read and the others are `grant_other_row`;
- short of the count, the grant **waits** on the voice of each holder not heard (a counted row gains
  voices without changing its row id, CC 2.6.1.9), never refuses; with no holder's voice at all it
  waits the same way;
- the bundle is the caller's (`BundleLookup::view`): held (the bundle in force or a predecessor in
  the held lineage, so a grant is counted where it was made and stands until ended), not held
  (`waiting:bundle`), or on a fork the reader holds void (`grant_head_void_fork`).

**Scope (CC 4.5.5, `scope_satisfies`).** The check asks "may this key attest family F", F =
`provenance:build_manifest`. A held `infra:attest` satisfies it; a held `infra:attest:F` satisfies
it; nothing else does. The match is on whole tokens across a `:` boundary: a child never satisfies
its parent (`infra:attest:F:x`), and `infra:attest_assurance` or `infra:attest:F_x` is another
capability. `grant_confers_build` then requires `build.project` among `projects`; a grant with no
`projects` confers a build manifest for no project.

The genesis bundle's charter `scope` holding `infra:attest` (`edition2::genesis::REQUIRED_SCOPE`)
is the root's scope and confers nothing on a pipeline. The minted genesis seats three holders and
one serve seat; nobody holds a pipeline grant yet. **One holder ceremony grants both pipelines**, the
server's and verify's, counted over 2 of the 3 holders, and scheduling it is Eric's (§13).

### 4.3 The owner-binding and the acceptance (two consents)

A conferral is two consents. The second is the **owner's**, never the pipeline key's.

**The owner-binding (CC 3.2, rc22 462260c).** A `delegates_to(owner → K)` row of family
`ownership:{relation}:{target_kind}:{version}`, authored by the owner, CWT `sub` the owned key.
`family_shapes::check_owner_binding` holds its shape: `author` an identity reference;
`delegation_purpose: "owner_binding"`, its one purpose; `scope`, where carried, a non-empty set;
`delegation_valid_until`, where carried, later than `delegation_valid_from` (or `asserted_at`);
`cohort_scope` one of the seven values, carrying `community_id` for `community` / `affiliations`
and `family_id` for `family` and no other group member; and `on_behalf_of`, a group reference for a
key held for an organisation, carried only with `refs` whose one role is `head` (the affiliation's
roster version), and `refs` carried only with it. `read_owner_binding` reads one statement of the
row, the owner's or the key's own first-binding cosign over the same payload (one row id), into an
`OwnerBinding { owner, key, row_ids, other_bindings }` holding that one row. One owner may hold
several live bindings of a key (the row where it first placed the binding and each re-signing at
another scope); they are one ownership (CC 3.2). The caller decides which held bindings are live
and folds them with `GranteeOwner::of_live(live, other_bindings)`: one owner across the live rows is
`Owned` with every live row id; none live, or live rows naming two owners, is `NoOwner`.
`other_bindings` is every other binding of the key the reader holds, ended or another owner's.

**The acceptance.** A `scores` row of `membership:{stage}`, dimension `membership:acceptance:v1`
(or `membership:decline:v1`), authored by the owner the binding names, CWT `sub` the grantee, and
`refs.answers` the grant (`family_shapes::check_reply`: no `refs.target`, no `refs.head`, no
`proposal_hash`). It cites the owner-binding it is made under in `refs.also.cites`, and stands when
it cites exactly one held owner-binding of the grantee's key, that row is live, and its owner is the
acceptance's signer and the one owner the live bindings name. Citing an ended or another owner's
held binding, two held bindings (two live rows of the one owner included), or none is
`acceptance_other_binding`: each ownership needs its own acceptance (CC 3.1.2.1), and an owner that
withdraws the row its acceptance cites ends that acceptance's footing even where another of its rows
keeps the ownership, until it accepts again citing a live row. Citing only rows not held waits on
them (`waiting:row`). A key with no owner has no acceptance: `grantee_has_no_owner`, except that an
acceptance citing only rows the reader does not hold, with no live binding held, is
`waiting:owner_binding`. The
owner's `trust:accepts:v1` edge is a separate thing: it roots the owner's nodes in the root and is
not consent to any grant.

**Answers and ends** (`grant_in_force`, deciding through `count::conferral_in_force`):

| Held | Reading |
|---|---|
| a counted `withdraws` of the grant by a strict majority of the holders of the bundle it names in `refs.head` (`read_grant_withdrawal`) | `grant_withdrawn` |
| an acceptance and a decline, both standing | `grant_contested` (CC 3.1.3.2, CC 2.7.7 rule 6): neither counts |
| the same, with the decline withdrawn by the owner | the acceptance decides: in force |
| the same, with the acceptance withdrawn | `grant_declined` |
| a decline alone | `grant_declined`, terminal for that grant; the holders grant again |
| an acceptance, withdrawn by the owner (`read_reply_withdrawal`: authored by the acceptance's author, `refs` exactly `{target}`, no `head`) | `acceptance_withdrawn` |
| an acceptance standing | in force |
| neither | `waiting:acceptance` |

Rows carry no arrival order, so an acceptance appearing after a decline is the contested case,
never a revival. Revoking the pipeline's **key** is a separate act that ends what the key signs
afterwards (`revoked_after`). A reader's own un-trust of the root ends every grant under it for that
reader; for verify the root is its baked anchor.

### 4.4 The build row

`read_build_row` reads a `scores` row (a later build at the same three is a `supersedes`) of family
`provenance:build_manifest:{target}`, authored by the pipeline (`author` = `iss` = CWT `sub`):

| Member | Rule |
|---|---|
| `dimension` | exactly `provenance:build_manifest:{target}:v1`, `{target}` the family's leaf |
| `build` | closed: exactly `project` (`[a-z0-9-]`, 1..=64 bytes), `version` (1..=64 bytes, compared byte for byte), `manifest_hash` (a hash-digest, `[-16, h'…32 bytes']`), `manifest_size` (≥ 1) |
| `evidence_refs` | holds `manifest_hash` |
| `refs.head` | the bundle in force when the row was signed: the grant's, or a later bundle of the grant's lineage (`BundleLookup::descends`) |
| `refs.target` | on a `supersedes`, the earlier row at the same (signer, project, version, target) |
| `refs.also.stands_on` | a set of exactly one row-ref (`edition2::check_refs`): the owner's acceptance the row stands on |

Every other payload member is open. One row stands per (signer, project, version, target); a later
row at the same three is a `supersedes` naming the earlier, and two standing rows at the three with
different `build` outside one `supersedes` chain are both refused (`build_manifest_equivocation`,
CC 2.7.7 rule 2).

**Two standings (CC 2.4.1.1 "An act names its head"; CIRISKernel fa1dc1d §J).** The build row
stands on the acceptance it names in `refs.also.stands_on`, and the acceptance on the owner-binding
it cites. So the row's standing is the grant as this owner accepted it under this binding. A row
naming no acceptance counts for nobody (`build_row_stands_on_nothing`, final); a row naming a held
row that is not the valid acceptance of this grant is the same; a row naming a row not held waits
on it (`waiting:row`). The binding's `sub` must be the grantee, which must be the build row's signer
(`owner_binding_other_key`, `grant_other_grantee`).

### 4.5 Comparison against the running module (Phase 2)

- **Binary.** `registry::compute_self_hash` hashes the file `self_module_path` names with
  `binary_format::canonical_binary_hash` (whole file on ELF and PE; the page-aligned `__TEXT` region
  on Mach-O), compared in constant time with the blob's `binary_hash`.
- **Functions.** `function_integrity::verify_functions` resolves the code base of the module holding
  `self_code_address`, which for a host is the host's image. Every entry must match; the
  opaque-failure rule of FSD-001 holds. The Android path still reads `text_section_offset`; the
  blob's offsets are base-relative (§6), so that path moves to the Linux base resolution with it.
- **iOS.** Function hashes do not survive App Store re-signing. The FFI's existing compensation
  (App Attest standing in for function integrity at L1) is unchanged.

### 4.6 Presenting

A running node's statement that it runs the build is `attestation:self_verify`, signed by the
running node about itself (CC, Q1). It cites the host pipeline's Contribution: `evidence_refs`
carries the manifest blob's digest, and the named row is the Contribution's row id. A node's
`ceg-boot-manifest/2` carries `build_manifest_row`, the build row's row-ref (§14, Q12). Verify
supplies the verified inputs (`manifest_row_id`, `manifest_hash`); the node signs.

## 5. How the host names itself (Phase 2)

**Configuration.** `VerifyConfig` gains `host: Option<HostIdentity>`, `HostIdentity { project:
String, version: String }`, under the descriptor's rules (§4.4). `VerifyConfig.project` keeps naming
verify's own registry namespace.

**FFI.** `ciris_verify_init_with_config(config_json)` taking `{ "host_project": "...",
"host_version": "..." }` (both or neither); `ciris_verify_init()` stays the zero-config form.
Python: `CIRISVerify(host_project=..., host_version=...)`. The host's wheel passes its own
distribution name and `__version__`.

**Why it is only a lookup key.** The pair selects which offline set to fetch. It decides nothing:
the blob must name the running file's measured `binary_hash`, so a false name finds a row about
other bytes (a refutation) or no row (absence); the reported project and version are the **row's**
(`manifest_project`, `manifest_version`), and the configured pair is echoed separately
(`host_project_claimed`, `host_version_claimed`) with `manifest_names_host` recording whether they
agree; a host naming an older version of itself matches only a row for the bytes running.

A host that configures nothing while embedded keeps `embedded_in_host: true`,
`error: EMBEDDED_NO_MANIFEST`, not a pass. Verify's own artifact needs no configuration: it looks
itself up as project `ciris-verify` at its `CARGO_PKG_VERSION`. A non-embedded install that
configures a host pair has it ignored and reported (`host_ignored_not_embedded: true`).

## 6. The manifest blob, `ciris-binary-manifest/1`

`edition2::build_manifest`, with its CDDL at
`src/ciris-verify-core/tests/vectors/edition2/build_manifest/binary_manifest_v1.cddl` (vendored by
CC as `manifests/binary_manifest_v1.cddl`) and its known answers in `binary_manifest_v1_vectors.json`
(10 valid blobs, 57 refusals, 5 function tables, 7 Merkle trees, from the independent
`gen_binary_manifest_v1.py`):

```
{ "format": "ciris-binary-manifest/1", "project": tstr, "version": tstr, "target": tstr,
  "binary_hash": bstr .size 32, "functions_root": bstr .size 32,
  ? "functions": { + name => { "offset": uint, "size": uint, "hash": bstr .size 32 } },
  "tool": tstr }
```

- **One blob per (project, version, target)**, covering the binary hash and the function table of
  one final shipped file, so the one build row that cites it covers both.
- **Not a signed object:** no `typ`, no key, no signature. CC 2.6.1.2's deterministic encoding, no
  floats, closed members, at most 1 MiB (checked before decoding).
- **A pure function of (file, project, version, target, tool).** It carries nothing about the run:
  `tool` names the generator and its version (`ciris-manifest-tool/23.6.0`) and nothing else, so two
  producers given the same final file emit the same bytes and anyone can recompute `manifest_hash`.
- **`format` is read first.** CDE orders keys by their encodings, which puts `"tool"` before
  `"format"` on the wire; `decode` checks `format` before any other member, so a blob of another
  format is `build_manifest_wrong_format`, never an unknown member.
- **Hashes are 32 raw bytes** (`bstr .size 32`; the format pins SHA-256). `binary_hash` is
  `canonical_binary_hash` of the final file.
- **`project`, `version`, `target`** are text exactly as given, compared byte for byte with the
  row's `build.project`, `build.version` and dimension `{target}` (`check_blob`).
- **The function table: one form.** `functions_root` is always carried: a Merkle tree of one leaf
  per function, leaves in the byte order of the function names, a leaf `CDE({name, offset, size,
  hash})` hashed `SHA-256(0x00 ‖ leaf)`, a parent `SHA-256(0x01 ‖ left ‖ right)`, a non-power-of-two
  count padded by repeating the last leaf (the locale tree of CC 3.1.2.1). An inline `functions` is
  optional and, when present, is recomputed against the root. Zero functions is refused.
- **Offsets are base-relative** (Q16, decided by verify; no metadata member): ELF `st_value −
  p_vaddr` of the executable `PT_LOAD` segment holding `.text`; Mach-O `n_value − vmaddr` of
  `__TEXT` (first slice of a fat file); PE the export's RVA. A function's `hash` is SHA-256 of its
  `size` bytes at that offset.

`ciris-manifest-tool generate-blob --binary --project --version --target [--filter] [--inline-functions]
--output` writes the blob from a final file (default filter `ciris_verify_`); it refuses a
function outside the file, a function of size 0, one name at two places, or no function.

## 7. The walk

`evaluate_build_standing(&StandingInput)` reads, as bytes it re-verifies: the build row's statement,
the blob, the grant's statements (every voice), any counted withdrawal of the grant, the owner's
answers, the owner's withdrawals of them, the grantee's owner (`&GranteeOwner`), the composers
view (`Option<&[&[u8]]>`, `None` for no view), a `KeyDirectory` for the pipeline's and owner's keys,
and a `BundleLookup`. It answers one `BuildStanding`: `stands`, the first refusal in link order, or
everything it waits on.

### 7.1 Order

1. **Build row** (§4.4). Waiting or refused here stops the walk.
2. **Blob against row** (`check_blob`): length is `manifest_size` before any hashing, then SHA-256
   is `manifest_hash` in constant time, then `decode`, then project / version / target equal the
   row's. Each mismatch is `build_manifest_descriptor_mismatch` naming the member; a codec refusal
   is the codec's token.
3. **Grant counted** (§4.2). Waiting does not stop the later links, so `waiting` lists everything
   missing.
4. **Grantee, head, scope, projects.** The grantee is the build row's signer; the row's `refs.head`
   is the grant's bundle or descends from it; a scope satisfies `provenance:build_manifest`;
   `build.project` is among `projects`.
5. **In force** (§4.3), and the row stands on the acceptance read (§4.4, two standings).
6. **Row state** (§7.4).

A refusal anywhere clears `waiting`. A refused link is final for that input; a waiting one is
retryable: hold what it names and read again.

### 7.2 Tokens

Refusals (`refused:{token}`). `{part}` is `build_row`, `grant`, `grant_withdrawal`, `acceptance`,
`acceptance_withdrawal` or `owner_binding`.

| Token | Fires when |
|---|---|
| `{part}_statement_invalid:{reason}` | the statement itself is Invalid under the row reader (CC 2.6.1) |
| `{part}_family:{fault}` | the statement breaks its family's rules (vendored family model) |
| `{part}_malformed:{member}` | a required member is missing or off its shape (for `build`, any member beyond the four) |
| `{part}_set_order:{member}` | a set (`scope`, `projects`) is unsorted or repeats an element (CC 2.6.1.2) |
| `{part}_wrong_row` | the row type or family is not the reading's |
| `{part}_voice_not_holder` | a statement under a key the named bundle seats, whose `iss` is not the holder seated there |
| `{part}_other_row` | a counted statement over another row than the one counted |
| `{part}_head_void_fork` | `refs.head` names a bundle on a fork the reader holds void |
| `build_manifest_descriptor_mismatch` | the blob's length, digest, project, version or target is not the row's |
| `build_manifest_oversize` | the blob is over 1 MiB |
| `build_manifest_not_deterministic` | the blob is not one deterministically encoded item |
| `build_manifest_float` | the blob carries a float |
| `build_manifest_not_a_map` | the blob's top level is not a map |
| `build_manifest_wrong_format` | `format` is not `ciris-binary-manifest/1` |
| `build_manifest_unknown_member` | a member the blob or a function entry does not admit |
| `build_manifest_missing_member` | a required blob member is absent |
| `build_manifest_malformed` | a blob member of the wrong type or out of range |
| `build_manifest_empty_functions` | a function table of zero functions |
| `build_manifest_duplicate_function` | one name twice in a producer's table |
| `build_manifest_functions_root_mismatch` | the inline table's root is not `functions_root` |
| `grant_other_grantee` | the grant's grantee is not the build row's signer |
| `build_row_other_head` | the row's `refs.head` is neither the grant's bundle nor a later bundle of its lineage |
| `pipeline_grant_out_of_role` | a grant carrying `projects` carries a scope beyond the two attest scopes |
| `build_manifest_scope_not_granted` | no scope the grant carries satisfies `provenance:build_manifest` |
| `build_manifest_project_not_granted` | `build.project` is not among `projects`, or the grant carries none |
| `grant_withdrawn` | a counted withdrawal of the grant is held |
| `grant_declined` | the owner's decline stands alone |
| `grant_contested` | the owner's acceptance and decline both stand |
| `acceptance_withdrawn` | the owner withdrew the acceptance |
| `acceptance_by_grantee` | the answer is signed by the grantee's own key |
| `acceptance_not_by_owner` | the answer's author is not the owner the binding names |
| `owner_binding_other_key` | the binding supplied names another key than the grantee |
| `acceptance_other_binding` | the acceptance does not cite exactly one held owner-binding of the grantee's key, or the one it cites is not a live binding by the owner |
| `grantee_has_no_owner` | the reader holds no live owner-binding of the grantee's key, or the live bindings name more than one owner |
| `build_row_stands_on_nothing` | the row names no acceptance in `refs.also.stands_on`, or a held row that is not the owner's acceptance of this grant |
| `acceptance_other_grant` | the answer's `refs.answers` names another row than the grant |
| `acceptance_other_grantee` | the answer's CWT `sub` is not the grantee |
| `build_manifest_withdrawn` | the pipeline's `withdraws` of the build row is held |
| `build_manifest_superseded` | a `supersedes` of the row at the same three is held |
| `build_manifest_equivocation` | another standing row of the signer at the same three with a different `build`, outside one `supersedes` chain |

Waits (`waiting:{token+token}`, sorted, once each):

| Token | Waits on |
|---|---|
| `key` | a signer's key record not held |
| `record` | a key record a rotation link names |
| `row` | a row a statement names (an unheld `stands_on`, an unheld binding the acceptance cites) |
| `voice` | the voice of each holder not yet heard on a grant short of its count |
| `bundle` | a bundle `refs.head` names that the reader does not hold |
| `grant` | no grant statement supplied |
| `acceptance` | no acceptance answering the grant |
| `owner_binding` | no live owner-binding of the grantee held, and an acceptance cites a row the reader does not hold |

### 7.3 Vectors

`src/ciris-verify-core/tests/vectors/edition2/build_standing/build_standing_v2.json` (117 cases,
statement pools `build_standing_pool_v1_{0,1}.json` and `build_standing_pool_v2_0.json`) from
`gen_build_standing_v2.py` (v1's case file is kept byte-identical and no longer replayed), independent of
verify, over the v5 row-statement, binary-manifest and v6 genesis-bundle generators. Holders A, B,
C, D; pipeline P (`node`); owners O, O2 (`user`); a second machine key Q; a stranger X and an owner
O3 with no key record. Its `kernel_counterparts` map ten cases to CIRISKernel's two-standings cases
(fa1dc1d §J: `grant_ended`, `names_bundle_alone`, `names_the_binding`, `under_the_new_owner`,
`before_the_new_owners_acceptance`, `old_owners_act_after_the_rebinding`,
`second_stint_of_one_owner`, `names_bundle_and_acceptance`); its `kernel_not_covered` names the
three Kernel cases that need receipts (§7.6).

### 7.4 Row state

`build_row_state(row, view, keys)` over every `withdraws`, `supersedes` and build row the caller
holds by the same signer:

- the signer's `withdraws` naming the row in `refs.target`: **withdrawn**, a node running that build
  fails;
- a build row of the signer at the same three that is a `supersedes` naming the row:
  **superseded**, a binary matching only the superseded manifest fails;
- another standing build row of the signer at the same three with a different `build`, not joined
  to the row by `supersedes` links among the rows held: **equivocation**, both refused. A withdrawn
  peer is not standing; a peer with the same `build` is no equivocation.

Statements of the view that read as none of these are counted in `unread` and decide nothing.

### 7.5 The withdrawal view

The revocation snapshot carries revoked keys and entities, never row withdrawals. A withdrawal
reaches the reader as the `withdraws` row itself, so Level 1 reads the row plane as well as the
snapshot.

| `withdrawal_state` | Meaning |
|---|---|
| `withdrawn` / `superseded` | a composer was held and verified; refused |
| `none_held` | a view was supplied and holds no composer naming the row |
| `unknown` | no view was supplied |

**Ruled (Eric, Q17):** `unknown` and `none_held` do not fail. A verified manifest stands, and the
view is always reported beside the verdict (Phase 2 adds its source and as-of instant, §8), so no
pass is silent about it. Consumer policy decides whether it needs `none_held` with a recent view.

### 7.6 Stated limits

- **No receipts.** The walk reads no receipts (CC 2.7.5 **settled**). A build row whose grant has
  ended, or whose acceptance is withdrawn, is refused, where Kernel keeps an act settled before the
  end standing ("counted but not in force", CC 2.4.1.1 "What stays in force"). The vectors'
  `kernel_not_covered` names the cases.
- **No `now`.** The walk takes no clock: a grant's `delegation_valid_from` / `_until` and an
  owner-binding's window are not compared with an instant. Key-record coverage is read from the
  rows' own instants by the caller's `KeyDirectory`.
- **The fold's, not the walk's.** Which binding of a key is live, whether a first binding's cosign
  is held, and whether `on_behalf_of` names an affiliation need rows the walk does not take; the
  caller decides them and supplies one `OwnerBinding` with `other_bindings`.
- **Unwritten in CC.** A **new** owner's decline against the old owner's acceptance after a
  re-binding is stated nowhere in CC and pinned by no vector.

## 9. The read route (Phase 2)

Server's route, `GET /v1/provenance/build/{project}/{version}/{target}`, returns one read-only
offline set that any node holding the rows can serve: the bundle the grant names (statements and
the rows it names), every statement of the build row, the blob, the pipeline's `key:record`, the
counted grant with every voice, the owner's acceptance, the owner-binding it cites, and the
`withdraws` / `supersedes` rows naming the build row (CC's list, Q19, with the owner-binding
the two standings need). Everything is bytes the
reader re-verifies offline from its anchor; any summary, `standing` or `served_by` member is
ignored. One call answers the withdrawal view (§7.5); a route that withholds a composer hides a
withdrawal from that reader and cannot forge a pass. CC 5.3.5's
`GET /v1/verify/build-manifest/{project}/{version}/{target}` is the earlier form's and retires with
it.

## 11. Threats

In the style of `docs/THREAT_MODEL.md` §3; proposed for that document as AV-63 onward.

#### HB-1: A host lies about its project or version

**Attack:** configure another project's name, or a newer version, to borrow its manifest.
**Mitigation:** a lookup key only (§5); the blob must name the measured hash, and reported project
and version are the row's. **Residual:** none; `manifest_names_host: false` is the trace.

#### HB-2: Stolen pipeline key

**Attack:** sign a build row for a modified host.
**Mitigation:** the row stands only on a counted, accepted grant listing its project. The holders
withdraw the grant by count, or the owner withdraws the acceptance; the pipeline revokes its key
(`key:revocation:v1`, `revoked_after`, carried by the snapshot). Custody of the key in hardware
raises the cost.
**Residual:** a node that has not received the withdrawal or revocation passes until it does (HB-6).

#### HB-3: A grant wider than `infra:attest`

**Attack:** a grant carrying more, so a pipeline compromise reaches further.
**Mitigation:** a grant carrying `projects` with any other scope is refused
(`pipeline_grant_out_of_role`); one without `projects` confers no build manifest. **Residual:** a
grant of the parent `infra:attest` satisfies every attest family; the ceremony grants the sub-scope.

#### HB-4: One pipeline attests another project's build

**Attack:** a pipeline granted for project A signs a row naming project B. **Mitigation:** the
grant's `projects` (`build_manifest_project_not_granted`). **Residual:** a set listing too much is
the holders' counted act.

#### HB-5: A forged or self-made acceptance

**Attack:** the pipeline key, a stranger or a former owner accepts the grant.
**Mitigation:** only the owner the binding names accepts (`acceptance_by_grantee`,
`acceptance_not_by_owner`), under the one binding it cites (`acceptance_other_binding`), and the
build row names that acceptance (`build_row_stands_on_nothing`). A re-binding needs a new
acceptance. **Residual:** which binding is live is the caller's fold (§7.6).

#### HB-6: A withdrawn build still running

**Attack:** keep running after the pipeline withdraws the build, relying on the node not hearing.
**Mitigation:** composers ride the offline set (§9); a held `withdraws` refuses. Every verdict
states `withdrawal_state`. **Residual:** an offline node, or a serving node that withholds the
composer, leaves `unknown` or a stale `none_held`; by Eric's ruling that still stands, reported and
never silent.

#### HB-7: Replay of an old manifest for a vulnerable build

**Attack:** run an old, never-withdrawn build and claim its version.
**Mitigation:** the row is genuine and the bytes are that build, so L1 truthfully passes for it;
`manifest_version` and `manifest_asserted_at_ms` say which. **Residual:** L1 proves which build
runs, not that it is safe; a minimum version is consumer policy.

#### HB-8: The registry serves a different blob

**Attack:** other bytes, or another length, under the row.
**Mitigation:** size, then full SHA-256 against the signed descriptor, before decode (CC 5.3.2.11).
**Residual:** denial of the pass only.

#### HB-9: A function manifest covering only a few functions

**Attack:** the blob lists few functions, so most code is unchecked in memory.
**Mitigation:** zero functions is refused; the whole-file hash covers every byte on disk.
**Residual:** the in-memory check covers exported functions only (95–96 `ciris_verify_*` on the
measured server builds); a coverage floor is consumer policy.

#### HB-10: Target or ABI confusion

**Attack:** a row for another target (simulator on device, glibc on musl, a triple for an ABI).
**Mitigation:** the row's dimension and the blob name one target; the binary hash binds one file.

#### HB-11: Equivocating rows

**Attack:** two rows for one (project, version, target), naming two binaries, shown to two readers.
**Mitigation:** a reader holding both refuses both (`build_manifest_equivocation`); the route serves
every standing row at the three. **Residual:** a reader shown one cannot tell.

#### HB-12: A grant voiced by non-holders or a void fork

**Attack:** sign the grant with keys of a forked or stale roster, or many stranger keys.
**Mitigation:** a voice counts only for a holder of the bundle named, under the key that bundle
seats; a bundle on a void fork refuses; strangers are not voices. **Residual:** a captured majority
of the holders.

#### HB-13: The host tampers with verify in its own address space

**Attack:** patch verify's code or result after load. **Mitigation:** the function check reads the
mapped image. **Residual:** inherent; remote readers rely on L2 and the node's signed
`attestation:self_verify`.

#### HB-14 (limit): An old build outlives its pipeline key

**Effect:** once the key has truly ended, the old build's row lapses unless a live row names it; a
fresh install of that build, with no live attester, finds no un-lapsed manifest. **Mitigation:** the
pipeline renews its record for as long as its builds are meant to run.

#### HB-15 (limit): The hard cut

**Effect:** from the Phase 2 release no install, embedded or verify's own, passes Level 1 until the
grant ceremony has run and the pipelines have published rows for that release. **Mitigation:** ship
Phase 2 only after both (§13). Until then every install reports which link is missing: fail-secure,
not a regression to unsigned trust.

## 15. Findings in the current code and docs

- **(a) Level 1 does not check the function manifest's signature.** `functions_valid` is computed
  by `UnifiedAttestationEngine::run_self_verification_with_manifests` (`unified.rs`), which calls
  `function_integrity::verify_functions` on the manifest `RegistryClient::get_function_manifest`
  fetched, with no signature check. The signature is checked only in the FFI constructor,
  `constructor::early_verify` → `run_verification` → `verify_manifest_signature` against
  `get_trusted_stewards`; its result goes to the response's separate `function_integrity` string and
  never reaches `functions_valid` or `l1_pass`. Phase 2 removes that path.
- **(b)** `release.yml` passes no `--filter` to `ciris-manifest-tool generate`; `ciris_verify_` is
  the tool's default.
- **(c)** `holds_bytes:sha256:{prefix}` is retired in rc22; the holder directory is `custody:ack:v1`
  (CC 3.1.3.3). FSD-006 stages 7 and 10 still name it.
- **(d)** FSD-006 §5 / §6 take standing from the serving node's walk; CC 3.1.2.1 and CC 5.3.4 make the
  reader evaluate it. This FSD replaces that model for Level 1.
- **(e)** `edition2::build_standing`'s module docs and `OwnerBinding`'s doc say verify has no
  edition-2 owner-binding reader; `read_owner_binding` reads the row (its shape through
  `check_owner_binding`). `grant_counted`'s doc names a `grant_no_voice` refusal that does not exist:
  a grant with no holder's voice waits on `voice` or `grant`.
- **(f)** A `recants` of a build row is not read by `build_row_state`: it counts as `unread`, and
  `WithdrawalState` has no recanted value.
